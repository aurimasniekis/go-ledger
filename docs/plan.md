- **B3 Enable Banking adapter** (ADR-0023): `internal/providers/enablebanking`; RS256 application JWT; consent, session, accounts, balances and paged transactions; ISO 20022 mapping with exact signed amounts; Enable Banking error codes classified into the banking taxonomy (expired or revoked consent, bank rate limit with 6 h guidance, outages); both D10 modes (app and developer) as per-mode configuration slots (`banking.enable_banking.app|developer.*`), keys from an environment secret or a file, parsed at `ledger serve` startup; offline tests against a fake Enable Banking server with synthetic fixtures, including full refreshes through the import engine. No live check (D20).
  - Follow-up: more than one application per mode; PSU headers for user-triggered refreshes (port change); connection endpoints and consent redirect (B4); periodic `Verify`/readiness; setup docs (B5).

- **A2 Passwords, sign-in and sessions** (ADR-0026): Argon2id (RFC 9106 parameters, bounded concurrency) in `user_passwords`; minimum length in bytes, no composition rules; uniform 401 `invalid_credentials` with one hash verification per attempt; in-memory failure limits per username and per address (IPv6 /64), 429 with Retry-After; server-side sessions (`sessions`, token stored as SHA-256) in a Secure, HttpOnly, SameSite=Strict cookie with idle and absolute timeouts; list and end own sessions (effective on the next request); setting a password ends the user's other sessions; CSRF for every cookie-authenticated write (origin check plus HMAC token), bearer tokens exempt; recent re-authentication (`x-ledger-recent-auth`) for user management and password changes; `ledger auth set-password` host command; audit of sign-in, re-authentication, session end and password change. Migration `0010_auth_sessions`, fixture `0009_commitments`.
- **A4 API tokens and bootstrap** (ADR-0029): `Authorization: Bearer ldgr_<43 base62>` tried before the session cookie; shown once, stored as SHA-256 with a prefix/last-characters hint, name, owner, grants or root, optional expiry, last use and revocation time (`api_tokens`); grants never above the creator's, root only for holders of every grant and always with a warning; own tokens under `/auth/tokens` (session, creation needs recent re-authentication), everyone's under `/tokens` (`tokens:read`/`tokens:write`); revocation on the next request; `ledger token create` host command for the first token on a fresh database (prints only the token on stdout); `token.created`/`token.revoked`/`token.write_used` (with `interactive_steps: skipped`) audited, recorder required wherever tokens authenticate. Migration `0012_api_tokens`, fixture `0011_commitment_occurrences`. A password change does not revoke tokens (D24); only a root token of the root account (the first user) may create tokens through the API, audited with `parent_token_id` (D25-1); re-enabling a user revives their unrevoked tokens (D25-2). A4e: a token-created token stores its parent (`parent_token_id`, migration `0018_token_parents`, fixture `0017_payment_matches`), expires no later than its parent and is revoked, audited, with its parent and all descendants (ADR-0029 amendment).
  - Defaults (12 bytes, 30m idle, 12h absolute, 10m re-auth window, 10 per username and 30 per address per 15m) are proposed, not operator decisions.
  - Follow-ups: A7 screens (sign-in, sessions, re-auth prompt, password change); A3 second factor in the sign-in flow; A4 token authenticator first, re-auth on token creation, whether a password change revokes tokens (done in A4, ADR-0029); A6 sessions through the same table.
- **A3 TOTP, recovery codes and required 2FA** (ADR-0030): RFC 6238 TOTP (SHA-1, 6 digits, 30 s, one step either side) with replay protection (last used step per user); secrets sealed with AES-256-GCM under an HKDF key from the KEK, bound to the user; ten 80-bit recovery codes shown once, stored as SHA-256 hashes, consumed on use; enrolment start/confirm, recovery-code regeneration and disabling under `/auth/two-factor` (recent re-authentication); two-step sign-in (202 challenge, `POST /auth/sign-in/second-factor`) with second-factor failures in the sign-in limits; `auth.require_2fa` confines a session without TOTP to enrolment, session, re-authentication and sign-out (403 `two_factor_enrollment_required`, `x-ledger-during-enrollment` in OpenAPI); `ledger auth reset-2fa` host command; every 2FA change audited; while TOTP is enabled, replacing, disabling or regenerating also needs a current TOTP or recovery code (D26-1a, counted in the sign-in limits). Migration `0012_totp` (to become `0013` when A4 lands), fixture `0011_commitment_occurrences`.
  - Defaults (one step of skew, ten recovery codes, 10m enrolment, 5m and five wrong codes per challenge) are proposed, not operator decisions.
  - Follow-ups: A7 enrolment, second-step and required-2FA gate screens; whether re-authentication should also ask for a second factor; an administrator reset route for other users; KEK rotation.
- **A6 Optional OIDC** (ADR-0033, decision D16): one provider (`auth.oidc.*`, secret from the environment or a file) through go-oidc and x/oauth2; authorization code flow with PKCE, state bound to a SameSite=Lax cookie and nonce; strict audience, azp, nonce, iat and auth_time checks on top of go-oidc's signature, issuer and expiry; explicit link while signed in, keyed by (issuer, subject) (`oidc_links`); provisioning off by default with a configured role; OIDC sessions are ordinary sessions (`sessions.method`), trusted for 2FA unless `auth.oidc.require_2fa`; `auth.password.enabled=false` refuses passwords and redirects `/sign-in` to the provider; OIDC re-authentication; unlink with recent auth and a remaining method; break-glass `ledger auth recovery-sign-in` and `ledger auth unlink-oidc` (docs/oidc.md); offline tests against a local fake provider (`internal/oidc/oidctest`). Migration `0015_oidc`, fixture `0014_payment_state`.
  - Follow-ups: A7 screens (provider button, link management, outcome parameters, OIDC re-auth prompt); A8 documentation; RP-initiated and back-channel logout, claim-to-role mapping, per-user password disable, administrator unlink (not built, see ADR-0033).

- **X1 Payment matches, manual matching, corrections, reversal** (ADR-0035): `payment_matches` allocation table (one row per transaction and occurrence with the allocated amount, D8 a) with origin (auto_rule, model_suggestion, user) and state (suggested, confirmed, rejected, reversed), append-only `payment_match_events` history; database constraints (one open match per pair, same currency on transaction, occurrence and allocation, outgoing booked reported transactions only for confirmations, allowed state changes, decisions never deleted) and exact-decimal checks in the write transaction (no over-allocation, no overpayment without `allow_overpayment`); confirmed matches on countable transactions are `bank_transaction` evidence (ADR-0031 seam); match, confirm, reject, unmatch, correct and reverse under `/payment-matches`, audited as `payment_match.*`; Go client methods. Migration `0017_payment_matches`, fixture `0016_device_cookies`.
  - Follow-ups: X2 engine and review queue (uses `matches.Store.Create`); X4 UI and MCP; CLI commands; linking bank reversal transactions to reversed matches; following `superseded_by` from pending suggestions.
- **X2 Automatic matching engine** (ADR-0038, decisions D9, D8, D5, D33): `internal/domain/automatch` (a pure, deterministic planner over a snapshot, plus a runner). Candidates need the same currency, a date within 7 days of the due date and an amount within 10% or the commitment's tolerance; the description score is a hint only. D9 safeguards: exact amount or short by at most the new per-commitment `match_tolerance`, booked, within 3 days, one candidate on each side, not already assigned. Everything else is an `auto_rule` suggestion whose reason names the failed safeguards. Pairs a person closed are never re-suggested; only the engine's own stale suggestions are dropped. It runs after every refresh that stored something (`bankimport.Options.AfterRefresh`), through `POST /payment-matching/runs` (audited `payment_matching.run`) and through `ledger matching run`. Store guard: automation cannot confirm a model suggestion. Migration `0020_commitment_match_tolerance`, fixture `0019_manual_payment_soft_delete`.
  - Follow-ups: X2b expr-lang rules; X3 TypeSafe suggestions; X4 review-queue UI and MCP; surfacing provider reversal signals as warnings (D33); refreshing a standing suggestion's reason.
- **A7 Auth and account UI** (ADR-0036): sign-in (two-step with 2FA), re-authentication prompt that repeats the action, 2FA enrolment (key and otpauth link, no QR code), recovery codes shown once with copy and download, regenerate and disable, required-2FA gate, sessions list and end, own API tokens (grants picker limited to the user's grants, root warning, token shown once and never reopenable, revoke), users, roles and all-tokens admin screens, password change. CSRF header on writes; `errors[]` mapped to fields. Minimal shell to be absorbed by U1.
  - Follow-ups: U1 takes over the shell, `RequireSession` and `QueryState`; a QR encoder (needs an ADR note); sign-in e2e needs a seeded database; TanStack Form with the first substantial form.
