# ADR-0029: Go client and CLI management commands

Status: Accepted (2026-11-21)

## Context

Task M2 needs a Go client for the Management API that the separate Terraform provider reuses (T2), and `ledger` subcommands that manage a running server through the public API with a token, with no private bypass. ADR-0011 chose a hand-written, spec-first OpenAPI document and left a stricter check of schemas to M2. API tokens (A4) are built in parallel, so the server side of bearer authentication is not part of this task.

## Decision

1. **Location and shape.** The client is `github.com/aurimasniekis/go-ledger/pkg/ledgerclient`, a public package in the application module. It imports nothing from `internal/`, so the provider can import it. It has its own types (`Commitment`, `User`, `Money` as decimal strings, ...), a `Client` built with `New(baseURL, token, options)`, typed errors, and ETag / cursor helpers.
2. **Hand-written, tied to the document by tests; no code generation.** This follows ADR-0011 (spec-first, hand-written, a small dependency set). `openapi_test.go` loads the embedded `openapi.yaml` and fails when: an implemented operation's method, path, operationId or query parameters differ; a documented operation has neither a client method nor a reasoned entry in `notImplemented`; a response type's JSON members differ from its schema or miss a required member; the request and PATCH body members differ; an enum constant differs from the document; or an error code the client names is not in the `Error` enum. Adding an operation to the API therefore fails the client's tests until it is implemented or excluded with a reason. Not checked: field types and constraints (minimum, pattern), and response status codes. The server's own tests cover those.
3. **Concurrency.** Update and delete methods take the version explicitly and send it as `If-Match` (ADR-0011 §7, ADR-0015 §3). Updates are JSON Merge Patch (`MergePatch`, a `map[string]any`, so absent and `null` stay distinct). A stale version is `*APIError` with code `version_conflict` and `Reconciliation` (current version, current object via `DecodeCurrent`); any other 409 is `IsConflict`. Errors keep the status, code, field, every per-field error and the request ID, and never contain the token.
4. **Pagination.** `Page[T]`, `ListOptions`, and `Walk` / `Collect` (an `iter.Seq2`) walk every page with the filters held fixed, as cursors require; `AllUsers`, `AllCommitments`, `AllOccurrences` and `AllAudit` wrap them.
5. **Token safety in the client.** Only `Authorization: Bearer`. Redirects are never followed. A plain `http://` URL is refused for a non-loopback host unless `WithInsecureHTTP` is given. Response bodies are limited to 8 MiB.
6. **Covered resources.** me, grants, users (list, get, create, update), audit (list), commitments (list, get, create, update, delete) and occurrences (list, get). Deliberately not covered: cookie-session sign-in, session management and password changes (browser flows that need recent authentication, which a token is not meant to bypass; `ledger auth set-password` stays a host command). API tokens, TOTP/OIDC and payment state are added to the `operations` table with their tasks; no shapes are guessed here.
7. **CLI.** `ledger me | grants | users | commitments | occurrences | audit <verb> [flags]` in `cmd/ledger/mgmt*.go`. They use `ledgerclient` only; a test fails if those files import `database/sql` or any `internal/` package, and every operation passes through the server's grants. Output is a human-readable table or key list, or `--output json`. Lists take `--limit`, `--cursor` and `--all`. Updates and deletes use `--version N`, or read the object just before writing when it is omitted (a change in between still fails with a conflict that tells the user the new version).
8. **Connection settings** are read per command: URL from `--url`, `LEDGER_URL`, the client config, then `http://127.0.0.1:8080`. The token comes from `--token-file`, `LEDGER_TOKEN`, the client config's `token_file`, then its inline `token`. The client config is a small YAML file (`url`, `token_file`, `token`, `output`; unknown keys are errors) at `--client-config`, `LEDGER_CLIENT_CONFIG` or `$XDG_CONFIG_HOME/ledger/client.yaml` (`~/.config/...`). It is separate from the server's configuration (ADR-0004) on purpose: the server's keys and `config.example.yaml` describe a process that serves, and a client machine may not have them. An inline token in a file readable by group or others is refused; a token file readable by others gives a warning. The token is never printed, logged or put in an error.

## Consequences

- The bearer-token authenticator is A4's. CLI tests use a test authenticator that maps fixed bearer values to test principals; they prove the CLI sends the header, that grants are enforced server-side and that nothing prints the token, not that real tokens work. Re-run them against real tokens once A4 lands (T2 does this against a started server).
- The client duplicates the response shapes by hand. The tests catch member and enum drift, not a type or constraint change.
- Merging the client into the application module means the provider repository depends on the whole module's requirements. If that becomes a problem, `pkg/ledgerclient` can move to its own module without changing its import path of use.
