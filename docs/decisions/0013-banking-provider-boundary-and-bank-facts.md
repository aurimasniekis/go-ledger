# ADR-0013: Banking provider boundary and normalized bank facts

Status: Proposed (2026-11-20)

Numbering: 0011 (API conventions) and 0012 (outbox) are taken on `work`. The outbox merged first with migration 0003, so this change's migration is `0004_bank_facts`.

## Context

Ledger imports accounts, balances and transactions from banking-data providers, Enable Banking first. The plan (task B1) asks for a provider port, a capability descriptor, an error taxonomy, normalized tables kept apart from user data, and a fake provider, with finance packages never importing a provider package.

Inputs: decision D10 (the operator's meaning of *app mode* = unrestricted production application and *developer mode* = restricted production application limited to linked accounts; coexistence **per connection**; neither is the sandbox), D8 (pending only suggests; no hard deletes; explicit purge), D17 (bank data stale after 24 h; retries only for idempotent reads, at most 3, honour Retry-After), D5 and ADR-0005 (exact decimals with currency, no floats, UTC instants), ADR-0003 (forward-only migrations, `WriteTx`), and research note R1 on the Enable Banking API: account `uid` and session id change on every re-authorisation while the identification hash is stable; `entry_reference` is the transaction identity but may be missing, repeated, or present only once booked; `transaction_id` is not identity; continuation keys are bound to the session and query; an unlinked account in restricted mode is an empty list, not an error; expired sessions return `EXPIRED_SESSION`; bank rate limits return 429 `ASPSP_RATE_LIMIT_EXCEEDED`.

## Decision

1. **Port in the domain.** `internal/domain/banking` declares `Provider` (institutions, consent start/complete, accounts, balances, one page of transactions, end session), `Capabilities`, the normalized model, the error taxonomy, the idempotency keys and the persistence port `FactStore`. Adapters (`internal/providers/<name>`, Enable Banking in B3) import it; it imports no adapter.
2. **One `Provider` value per configured application.** A deployment may configure several applications (D10). `Capabilities` names the provider, the application, its `Mode` (`app` or `developer`), `Environment` (`production` or `sandbox`), account access (`all` or `linked_only`, derived from the mode), supported balance types, pending support, whether entry references are stable, consent and history limits and the background-fetch limit. Zero numbers mean unknown.
3. **Error taxonomy.** Adapters return `*banking.Error` with a kind: `reconnect_required` (with a reason: consent expired, consent revoked, session invalid), `rate_limited` (with `RetryAfter`), `retryable`, `permanent`; Ledger's own cancellation is `canceled`. `Classify` treats a deadline or network timeout as retryable and any other unclassified error as **permanent**, so a forgotten classification cannot cause a retry storm. Only `reconnect_required` changes a connection's status (`StatusAfter`). Sentinels (`ErrReconnectRequired`, `ErrConsentExpired`, `ErrRateLimited`, `ErrRetryable`, `ErrPermanent`) work with `errors.Is`.
4. **Sensitive values.** IBAN, BBAN, masked PAN, other identifiers, per-session account handles, session references and authorisation codes are `banking.Sensitive`: every fmt verb, slog and JSON/text marshalling print `[REDACTED]`; only `Reveal` returns the value (the store and the originating adapter). `*banking.Error` messages carry provider, operation, kind, reason and provider error code only; the wrapped cause is not printed. Store errors name ids, positions and fields, never values, descriptions or counterparties.
5. **Tables** (migration `0004_bank_facts`, all STRICT, ULID ids checked with `store.IDCheck`, conventions of ADR-0003/0005):
   - `bank_connections`: provider, application, mode, environment, account access, institution, status (`pending`, `active`, `reconnect_required`, `failed`, `disconnected`), consent state (pending redirect), session reference, consent expiry and grant time, last error kind and code, `version` (Ledger-managed row, optimistic concurrency per M1).
   - `bank_accounts`: provider, external id (stable across sessions), per-session handle, identifiers, name, product, currency (`XXX` for unknown or multi-currency), first/last seen, no-longer-reported.
   - `bank_balance_snapshots`: append-only (trigger); normalized type plus the provider's code, exact amount and currency, optional reference date, `obtained_at`. An unknown balance is no row, never zero.
   - `bank_transactions`: provider, dedupe key and kind, entry reference, provider transaction id (provenance only), normalized and provider status, `source_amount`/`source_currency` exactly as reported (signed, negative = money out), optional instructed (original foreign) amount, booking/value/transaction dates, raw description, counterparty, `imported_at` (first import, immutable), `last_seen_at`, `no_longer_reported_at`, `superseded_by` (pending row replaced by a booked one).
   Bank facts (`bank_accounts`, `bank_balance_snapshots`, `bank_transactions`) carry no `version`: they are provider-owned, written only by the import path and not edited through the API, so they are listed in `unversionedTables` with that reason. Triggers also keep a transaction's `provider` equal to its account's (an account's provider is immutable) and `superseded_by` within one account.
   `bank_connections` is Ledger-managed and versioned (M1). User-initiated changes, disconnect (`DisconnectConnection`) and purge (`PurgeConnection`), take an expected version and go through `store.UpdateVersioned` / `store.DeleteVersioned`, failing with `resource.VersionConflictError` when the row changed. Provider-driven transitions (activate, begin reconnect, failure or expiry status changes) are made by the import and consent flows from state they have just read; they bump `version` without comparing it, because a provider-driven write reflects what the provider just reported and must not fail on a racing user edit; a user holding the old version then gets a conflict and re-reads.
6. **Idempotency keys.**
   - Account: `(provider, external_id)`. An account reported by another connection of the same provider is moved to it (outcome `moved`), keeping its id and history, so one real account is never imported twice.
   - Transaction: `(account_id, dedupe_key)`, built by `banking.KeyTransactions` over one account's whole fetch window: `ref:` + hash(entry reference, amount, currency) or, without a reference, `fb:` + hash(date, amount, currency, description, counterparty); then `#n`, numbering items with the same hash. The amount is in the reference key because banks may repeat references. Status is in neither key, so an item becomes booked in place when its reference (or its whole content) is stable. Keys are hashes and hold no text.
   - Balance: none; every fetch appends.
7. **Upsert rules.** A new key inserts. A known key updates status, dates, description, counterparty, detail id and instructed amount, sets `last_seen_at` and clears `no_longer_reported_at`. A booked row reported as anything else keeps its booked facts (`kept_booked`). Triggers make identity, source amount and `imported_at` immutable and forbid leaving `booked`.
8. **Separation from user data and purge.** User data (corrections, matches, manual payments, categories) lives in its own tables and refers to bank facts with `ON DELETE RESTRICT`; a schema test fails on any foreign key to a `bank_*` table with another delete action or a cascading update. Bank facts are deleted only by `PurgeConnection`, one transaction that deletes a connection's transactions, balances, accounts and the connection, and fails with `ErrPurgeBlocked` (deleting nothing) while user data refers to any of them. The purge first clears `superseded_by` of the purged accounts' transactions (SQLite checks the self-reference per row, so deletion order would otherwise matter), and `ErrPurgeBlocked` is derived from the SQLite foreign-key constraint error code, not from message text. The purge command (D8) calls it after ending the provider session.
9. **Fake provider** in `internal/domain/banking/bankingtest`: deterministic dataset (`Standard`), either mode, injectable clock, page size, empty first page, continuation keys bound to session, account and window, per-session handles, expiry, revocation, ended sessions, refused/forged consent, queued failures of every kind, and dataset mutation (for example `BookPending`). It lives under `internal/domain` so finance tests may use it while lint and tests forbid every real adapter.
10. **Enforcement.** depguard forbids `internal/providers` in `internal/domain/**` (existing) and now in `internal/store/**`; `internal/domain/boundary_test.go` also fails on transitive imports from either tree, and proves itself on a synthetic module. The float ban covers `banking` and `bankingtest` (type-checked) and `store/bankfacts` (name and literal scan, since it links the SQLite driver).

## Why

- A port per configured application keeps D10's per-connection mode simple: the connection stores which application and mode it was made with, and the mode stays visible even if configuration changes later.
- Keying accounts on the stable external id rather than the session handle is what makes re-authorisation (new session, new uids) re-use the same rows, as R1 requires.
- The transaction key had to work without a reliable entry reference. Including the amount resolves documented reference repetition deterministically, without depending on what else is in the batch; leaving status and dates out of the reference key keeps the common pending-to-booked path in place.
- Defaulting unclassified errors to permanent is the conservative choice for a provider whose banks limit background fetches to about four a day.
- `ON DELETE RESTRICT` everywhere plus one explicit purge path makes "a refresh cannot erase a user decision" a database property, not a convention.

Rejected: keying transactions on `transaction_id` (R1: not stable); one global account key across providers (identifiers differ per provider); storing raw provider payloads (sensitive, and nothing needs them yet); integer minor units (ADR-0005); a separate fake under `internal/providers` (finance tests could not import it under the boundary rule).

## Consequences

- **Import engine (B2)** owns: fetching windows that cover whole days and keying all pages of a window together; last-success and attempt timestamps and the 24 h staleness (D17); marking accounts and transactions the provider stopped returning as no longer reported (D8), and setting `superseded_by` when a pending item without a stable reference reappears booked under a new key; retry policy by error kind; keeping provider calls outside `WriteTx`.
- **Known limitations.** The `#n` ordinal of identical items is stable only while a fetch returns all of them; if a provider drops one of two identical pending items the remaining one can move from `#2` to `#1` (a pending row updated or a duplicate pending row, later marked no longer reported). A bank that repeats one entry reference for two transactions of the same amount merges them. A pending hold whose amount changes when it books (FX, tips) has a different entry-reference key, because the amount is part of it and `source_amount` is immutable: it becomes a second row, and both rows exist until B2 marks the pending one no longer reported or superseded. **B2 and the outlook must exclude pending, superseded and no-longer-reported rows** so a hold is never counted twice. A bank that changes the scale of an amount (`1.5` vs `1.50`) between fetches would create a second row. An account moved between two concurrently active connections of the same provider follows whichever imported last. These are recorded rather than solved because R1 documents no better identity.
- Enable Banking specifics (JWT signing, PSU headers, status-code mapping, `strategy=longest`, `transactions_extended_history`) stay in the B3 adapter, which maps to this model and taxonomy.
- No HTTP endpoints, OpenAPI or audit entries yet: they arrive with the connection API and UI tasks once the API conventions (ADR-0011) are merged.
