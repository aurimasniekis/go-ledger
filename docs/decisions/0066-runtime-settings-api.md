# ADR-0066: Runtime settings through the Management API (D18 blanket coverage)

Status: Proposed (2026-11-22), revised after review the same day. Design only: no product code changes with it.

Decisions recorded with this revision:

- The operator approved, through a `scope-reduction` human action on 2026-11-22, that the deployment settings of point 2 stay configuration-only with a read-only API view, and that the tuning limits of point 3 stay constants in code.
- Control accepted the recommendations of points 19 (root token for sensitive writes), 21 (no revision table) and 25 (MCP write scope), and extended point 25: a matching rule that can auto-confirm is a sensitive write and is not exposed through MCP (point 8, rules).
- The review's findings on the reporting zone (points 6 and 22), sealed secrets (point 12), the sensitive-write gate (points 9 and 19), bank applications (point 8), secret pin sources (points 2 and 13), consent attestations (point 23) and the task table are encoded below.

## Context

Decision D18 (option B) makes the Terraform provider manage **all** user-configurable settings and user-defined objects, and the requirements ask for create, read, update and delete of every configurable object through the one public Management API that the UI, the CLI, Terraform and MCP share (requirements, Management API and Terraform sections; "identical validation and grants"). The provider's coverage inventory (terraform-provider-ledger ADR-0005, item B1) found that the API serves none of these:

- matching rules (expr-lang, decision D9; task X2b, not started);
- decision provider and model settings, and consent records (ADR-0060; tasks L7 and X3 own the routes and screens);
- application and planning settings (reporting zone and currency, freshness thresholds, refresh and rate settings);
- authentication options (password and session rules, sign-in limits, required two-factor, the OIDC provider);
- bank integration settings (the Enable Banking applications of decision D10: app mode and developer mode, per connection);
- Pulse publishing and other operational settings.

Today every one of them is a key of the configuration system (ADR-0004): one typed `config.Config` struct filled from defaults, YAML, the environment (with `.env`) and flags, validated once at startup, with secrets accepted only from the environment or a referenced file. The only value already kept in the database is the captured reporting zone (`settings` table, migration `0002_settings`, written by `reporting.Resolve` in `internal/reporting/reporting.go`). On the first start it is captured from `reporting.timezone` or, when that is empty, from the host's IANA zone. Later an empty `reporting.timezone` uses the stored zone. An explicit value that differs from the stored one **overwrites** the stored row, with a warning and a `settings.reporting_timezone_changed` audit entry (actor `system`). `reporting.Service` is immutable after `Resolve`, and `cmd/ledger/serve.go` passes `zone.Zone()` by value to the matcher and the API registration: changing the zone takes a restart today.

Constraints that apply: optimistic concurrency with `version`/ETag and 409 `version_conflict` (ADR-0011, ADR-0015); JSON Merge Patch (ADR-0015, ADR-0017); declared per-route access and a grant vocabulary with derived roles (ADR-0021); the append-only audit log with a fixed detail schema per action (ADR-0025); the hand-written client tied to the OpenAPI document by tests, and CLI commands through it (ADR-0032); MCP tools that are typed calls of API operations (ADR-0038); secrets sealed with the key-encryption key, as TOTP secrets are (ADR-0030); token escalation guarded by the root token of the root account (D25, D32, D34); no secrets in YAML, flags, logs, audit details or responses; tests offline.

This ADR decides which settings move into the database and the API, how they combine with the configuration files, and the shape every implementation task follows. It does not build anything.

## Decision

### 1. Two kinds of setting

1. **Runtime settings** are stored in SQLite, managed through the Management API (and so the UI, CLI, Terraform and, where point 9 allows, MCP), versioned, audited and applied **live**, without a restart. Every user-configurable product setting is a runtime setting unless point 2 names it.
2. **Deployment settings** stay in the configuration system only. They are the settings a running Ledger cannot change about itself, or that would let an API caller reach outside the product. Each has its reason:

| Keys | Why they stay deployment settings |
| --- | --- |
| `database.path`, `database.busy_timeout` | Needed to open the database the runtime settings live in. |
| `http.listen`, `http.management_listen`, `http.read_header_timeout`, `http.read_timeout`, `http.write_timeout`, `http.idle_timeout`, `http.shutdown_timeout`, `http.max_body_bytes` | Bound when the listeners are built, before the database opens; rebinding a listener from a request that arrives on it is not safe. |
| `http.trusted_proxies` | Describes the host's network, and decides which client addresses the per-address sign-in limit sees: an API caller who could widen it could spoof addresses and escape that limit. |
| `log.format` | The log handler is built before the database opens, and log pipelines parse it. (`log.level` is a runtime setting.) |
| `kek.value`, `kek.file` | The root of secret sealing (point 12). Storing it next to what it seals defeats it. |
| Every `*_file` key (`banking.enable_banking.*.private_key_file`, `auth.oidc.client_secret_file`, `events.pulse.creds_file`, `events.pulse.ca_file`, `decisions.providers.*.api_key_file`, `merchants.enrichment.remote.api_key_file`) | A host file path. The API never accepts a path: a caller could otherwise make Ledger read, and send to a server of the caller's choosing, any file the process can read. The value behind each path can instead be written through the API as a write-only secret (point 12). |
| The secret environment variables that exist today (`LEDGER_BANKING_ENABLE_BANKING_{APP,DEVELOPER}_PRIVATE_KEY`, `LEDGER_AUTH_OIDC_CLIENT_SECRET`, `LEDGER_DECISIONS_PROVIDERS_*_API_KEY`) | Still accepted from the environment, as today. Each one pins its secret (point 13). |

   The operator approved this list on 2026-11-22 (`scope-reduction` human action): these keys stay configuration-only and are visible read-only through `GET /api/v1/settings/deployment` (point 9).

3. **Fixed policy is not turned into settings.** The matching safeguards and windows (D9, D39: ±3 days, 7-day suggestion window, 10 % band), the outbox retry and retention limits (D17), the refresh retry count and daily budget, and the rate refresh limit (D-FX-R) are operator decisions written in code, not configuration. The operator approved on 2026-11-22 that they stay constants in code. Making any of them configurable later needs its own operator decision.

### 2. Precedence: configuration pins, the database fills in

4. The effective value of a runtime setting is, highest first: **flags, environment (real, then `.env`), YAML, the stored API value, the built-in default.** The configuration layers keep their ADR-0004 rules (empty means unset). The reporting zone has one more layer under the API value, the **captured** zone (point 6a).
5. A key set by any configuration layer is **pinned**. The API shows it with its source and `pinned: true`. A write that names a pinned key is refused with 409 `setting_pinned` (new error code), naming the key and the layer (`flag`, `environment`, `dotenv`, `yaml`, `file`), never the value. Unpinned keys of the same group can still be changed.
   - Today `config.Load` records sources as `default`, `yaml`, `env LEDGER_X`, `flag --x` and `file <path>` (`internal/config/load.go`), and a variable read from `.env` is also recorded as `env LEDGER_X`. `Result.EnvLoaded` already lists the names `.env` contributed, so S1a splits the label (`dotenv` for those names) from that list.
   - `cmd/ledger/serve.go` keeps only `res.Config` and drops `Result.Sources` after loading. S1a keeps the sources in the settings service so the API can report them. The `file` layer is the source of a secret read through a `*_file` key (point 13).
6. The stored value of a key that becomes pinned is kept, not deleted, and applies again when the pin goes away. The reporting zone is the one exception (point 6a).

6a. **Reporting zone.** Changing the zone reclassifies due dates and monthly views (D5, F9), so the zone never changes without an explicit, audited choice:
   - The zone captured at first start stays where it is today: the `settings` row `reporting.timezone`, written only by `reporting.Resolve` inside its one write transaction. It is not an API value. `sources` reports it as `captured`. It is never written into `setting_groups.stored`, so it never shows as `api`, Terraform never sees it as drift, and `DELETE /settings/reporting` does not remove it. A later start with an empty `reporting.timezone` reads the captured row and does not capture the host zone again, so a host zone change does nothing on its own (as today).
   - The effective zone is the pin, else the API value (`setting_groups` `reporting`, member `timezone`), else the captured zone. On a database with none of these, the first start captures as today.
   - **Today's overwrite behaviour is kept**, not changed to "pin and restore". When a configured zone is in force at startup, `Resolve` compares it with the **previous effective zone** (the API `timezone` member if one is set, else the captured zone), not with the captured row alone. If they differ, it overwrites the captured row with the configured zone, warns and audits `settings.reporting_timezone_changed` (from the previous effective zone, to the configured one; actor `system`), as it does today when the captured zone differs. Whenever a configured zone is in force, differing or not, it also removes a `timezone` member that the API set, in the same transaction (audited `settings.reset`, group `reporting`, field `timezone`, actor `system`), so an old API zone can never become effective again unseen. Taking the pin away later leaves the last configured zone in force with source `captured`. Reason: under the general rule of point 6, removing a configuration key would silently bring back an older API zone, a reclassification nobody chose. Existing deployments with no API zone keep exactly today's startup behaviour. Example the rule closes: captured Europe/Vilnius, the API sets UTC with `reclassify`, the operator then configures Europe/Vilnius: the previous effective zone is UTC, so the change is overwritten and audited and the API member is removed; removing the configuration later leaves Vilnius, not UTC.
   - A write through the API or `ledger settings reset reporting` that would change the effective zone (setting `timezone`, setting it to `null`, or `DELETE` of the group while an API zone differs from the captured one) is a **reclassification**. It is refused with 409 `reclassification_required` (new code), naming the current and the resulting zone, unless the request carries `"reclassify": true` (a write-only request member, never stored; `--reclassify` on the host command). The accepted change is audited `settings.reporting_timezone_changed` (from, to) with the person's or token's identity, in the same transaction as the write. Changing `reporting.currency` follows the general rules.
   - Live apply (point 16) needs a redesign of `reporting.Service`, which S3 owns. The service publishes the zone through the settings snapshot. The matcher, the API handlers and every other consumer that receives `zone.Zone()` once at startup read the current zone for each operation instead. Work in flight finishes with the zone it started with.
7. Why this order: nothing an existing deployment sets changes meaning; the operator keeps a break-glass path for every runtime setting that does not need the API (set the variable, restart; for example `LEDGER_AUTH_PASSWORD_ENABLED=true` after an OIDC mistake, next to the existing `ledger auth recovery-sign-in`); and a Terraform plan against a pinned key fails loudly instead of drifting silently.

### 3. Groups and objects

8. Runtime settings are grouped by the component that consumes them. **Singleton groups** have one representation each, at `/api/v1/settings/{group}`:

| Group | Keys (today's configuration keys) | Grant | Sensitive (point 11) |
| --- | --- | --- | --- |
| `reporting` | `reporting.timezone`, `reporting.currency` | `settings` | no |
| `banking` | `banking.redirect_url`, `banking.consent_ttl`, `banking.stale_after`, `banking.refresh.enabled`, `.interval`, `.request_cooldown`, `.max_backoff`, `banking.enable_banking.base_url` (the shared default of point 8's bank applications) | `settings` | `redirect_url` and `base_url` |
| `rates` | `rates.enabled`, `.base_url`, `.source`, `.refresh_interval`, `.stale_after`, `.timeout` | `settings` (not the existing `rates` resource: see point 18) | `base_url` only |
| `merchant_enrichment` | `merchants.enrichment.remote.*` except `api_key_file`; `api_key` write-only (a new `config.Config` field, point 13) | `integrations` | yes |
| `auth` | `auth.password.*`, `auth.session.*`, `auth.sign_in.*`, `auth.require_2fa` | `settings` | yes |
| `oidc` | `auth.oidc.*` except `client_secret_file`; `client_secret` write-only | `settings` | yes |
| `pulse` | `events.pulse.enabled`, `.url`, `.source`, `.name`; `creds` write-only (the .creds content) and `ca_pem` (public, readable), both new `config.Config` fields (point 13) | `integrations` | yes |
| `mcp` | `mcp.enabled`, `.requests_per_minute`, `.burst`, `.max_request_bytes` | `settings` | no |
| `logging` | `log.level` | `settings` | no |
| `alerts` | `alerts.channels`, `alerts.consent_horizon_days`, `alerts.interval` | `settings` | `channels` (it names where alert data is sent) |

   **Keyed objects** (a fixed set of keys, no create or delete; `DELETE` resets to the defaults):
   - `/api/v1/decision-providers/{provider}` (`openrouter`, `openai`, `anthropic`, `typesafe`): `api_key` write-only, `allowed_upstreams` (OpenRouter). Grant `integrations`, sensitive.
   - `/api/v1/decision-tasks/{task}` (the ADR-0060 registry): `enabled`, `provider`, `model`, `capability`, `timeout`, `monthly_requests`, `retries`, `auto_apply`, `fields`, `fallback`, with the ADR-0060 validation (capability, excluded fields never allowed, auto-apply only for categorisation). Grant `integrations`, sensitive (it decides what leaves the process).

   **Collections** (create, read, update, delete, ULID identifiers per ADR-0011):
   - `/api/v1/bank-applications`, `/api/v1/bank-applications/{application}`: the Enable Banking applications of D10, **addressed by name**. The existing `GET /bank-applications/{application}/institutions` (`internal/httpapi/bankconnections.go`) is keyed by the application's name, and every connection records that name, so item routes use the same `{application}` parameter. A ULID `id` (ADR-0011) is a read-only member, the stable key of the row and of its sealed secrets (point 12), but it is not the address.
     - Members: `id`, `name` (1 to 64 of `[a-z0-9_-]`, the existing rule), `provider` (`enablebanking`), `mode` (`app` or `developer`), `environment` (`production` or `sandbox`), `app_id`, `base_url` (optional; when absent the application uses the shared `banking.enable_banking.base_url` of the `banking` group, which is one key today, `internal/config/config.go`), `enabled`, `private_key` write-only, the read-only `public_key_sha256` derived from it (so the person can compare with the Control Panel without the key leaving), `source` (`config` or `api`), `version`, plus the existing read-only members (account access, capabilities).
     - The two configured slots (`banking.enable_banking.app`/`developer`, when enabled) appear in the list with `source: config` and cannot be written (409 `setting_pinned`). An API application may not take the name of a configured one (409 `conflict`).
     - Renaming (`name` in a patch changes the address) or deleting an application that any connection records is 409 `conflict`; disabling it is the alternative.
     - **The list shows disabled applications too**, with `enabled: false`. Today `GET /bank-applications` lists only the applications that have a provider, which means only enabled ones. Starting a connection, reconnecting and listing institutions with a disabled application are refused as an unknown application is refused today. Existing connections keep their data and show as disconnected until it is enabled again.
     - **Grants:** `GET` on the collection and an item stay `connections:read`, the grant of the existing routes, because the connect flow needs them. Creating, updating and deleting need `integrations:write` and are sensitive (point 19). Both grants are administrator-only.
   - `/api/v1/decision-consents`: list, grant (`POST`), get, revoke (`POST /{id}/revoke`); a consent is never edited. Members per ADR-0060 point 5 (provider, purpose, fields, terms version) plus the attestations the research asks for (for example OpenRouter "ZDR only"). Attestations need a schema change (point 23). Grant `integrations`, sensitive. The granting actor must be a person or a token acting as one (D42 3a), never `system` (ADR-0060 N5). The schema still allows `granted_by_kind = 'system'` (migration `0031_decision_providers`), so the service enforces this rule and a test pins it.
   - `/api/v1/rules`: the expr-lang rules of D9, built by **X2b**, which owns the rule language, evaluation and the dry-run endpoint. This ADR fixes only what the API must look like so that Terraform and MCP can rely on it: a collection with ULIDs, `version`, merge-patch, `expression` compiled and refused at write time (400 naming the position, never echoing bank text), `purpose` (`matching` or `categorisation`), `confirming` (D9: only a rule the person marks confirming may auto-confirm, and it still passes every D9 safeguard), `priority`, `enabled`, archive-first like organisation definitions. Grant `rules` (administrator-only: expressions hold bank-text fragments, which D29 keeps from read-only users).
     - **A confirming rule is a sensitive write** (point 19), because it can confirm payments without a person (D9). Sensitive writes are creating a rule with `confirming: true`, changing `confirming` to `true`, and changing `expression`, `purpose` or `priority` of a rule that is confirming, or enabling or unarchiving one. Those writes are not exposed through MCP (point 25). Creating and editing non-confirming rules, and turning `confirming` off, are ordinary `rules:write` writes.

### 4. Representation and OpenAPI shape

9. Every settings resource follows ADR-0011 and ADR-0015:
   - `GET` returns the **effective** values as top-level members with the configuration types (durations as strings with a unit, enums, lists), plus read-only `version`, `updated_at`, `sources` (a map from member to `default`, `api`, `captured` (the reporting zone only, point 6a) or one of the configuration layers), `pinned` (the pinned members) and `apply_state` (point 17). `sources` reports the configuration layers by the loader's `config.Layer` names, so a variable from the real environment is `environment` and one from `.env` is `dotenv` (the loader's own labels stay `env LEDGER_X`; the layer is what the API shows).
   - `PATCH` is `application/merge-patch+json` with `If-Match` (or `version` in the body); `null` removes the stored value, so the member falls back to configuration or the default. Read-only members in a patch are 400. An empty patch changes nothing and keeps the version (ADR-0017 rule).
   - `DELETE` on a singleton or keyed object needs `If-Match` and resets every unpinned member to its default (the Terraform destroy of a settings resource).
   - A singleton or keyed object **always exists** for the API: Terraform creates it by reading it and patching (adopt), and imports it by its group name. Its `setting_groups` row is created on first write. Until then `GET` synthesises the representation with `version: 1` from the effective configuration. The first `PATCH` (or `DELETE`) must carry `If-Match: 1`, and the service inserts the row with version 2 inside the write transaction; a concurrent first write loses on the unique `name` and gets 409 `version_conflict`. `DELETE` without a row changes nothing and keeps version 1.
   - **Write-only secrets**: a member such as `client_secret` is `writeOnly: true` in OpenAPI 3.1 and is never returned. Its read-only companions are `client_secret_set` (bool), `client_secret_set_at` and `client_secret_source` (`api`, `environment`, `dotenv`, `file`, or absent). Writing `null` clears a stored secret. A secret's value is never compared, hashed into a response or echoed in an error.
   - `GET /api/v1/settings` lists the groups with version, `updated_at` and whether anything is pinned. `GET /api/v1/settings/deployment` (grant `settings:read`) returns the deployment settings of point 2 with their sources; secrets as `set`/`unset` only. It is the read-only view Terraform and the UI use for them.
   - Errors: field problems are 400 `validation_failed` with per-field errors using the configuration key names; a combination that breaks a cross-field rule (for example `password.enabled=false` without usable OIDC, point 19a) names every field involved. New codes: `setting_pinned` (409), `secret_unreadable` (409, point 12) and `reclassification_required` (409, point 6a).
   - Access is declared, not hidden in handlers. Today the root-token rule is a hand-written call (`refuseUnlessRootToken`, `internal/httpapi/users.go`) and the OpenAPI parity check in `internal/httpapi/openapi.go` compares only `x-ledger-access`, `x-ledger-recent-auth` and `x-ledger-during-enrollment` with the route. S2 adds the declarative mode of point 19 and its `x-ledger-root-token` extension to that check.

### 5. One validation, one effective configuration

10. The effective runtime configuration **is `config.Config`**. The loader gains the stored layer between the defaults and YAML (two phases at startup: load configuration, open the database, read the stored layer, merge, validate the whole). Every API write builds the would-be effective configuration from the stored values plus the patch, runs the **same** validation that `ledger config check` and startup run (ADR-0004 rules, including the cross-field and network checks), and only then commits. So the API, the CLI, Terraform, MCP and the configuration files accept exactly the same values, and `config.example.yaml` stays the reference for every key (each key's description says whether it is a runtime setting).
11. **Startup with invalid stored settings** (for example after an upgrade tightened a rule) is refused with a message naming the group and the host command that fixes it. New host commands, which open the database directly and so need the server stopped (instance lock, ADR-0019): `ledger settings show [group]` and `ledger settings reset <group> [--key k]`, both audited with actor `system`. `ledger config check` shows the stored layer and the source of every key when the database is readable.

### 6. Secrets in the database

12. A secret written through the API is sealed with the ADR-0030 sealer (`auth.NewKEKSealer`, `internal/domain/auth/seal.go`: AES-256-GCM, a key derived from the KEK with HKDF-SHA256, the format `v1.` + base64url(nonce || ciphertext)) and stored in `integration_secrets` (`owner_type`, `owner_key`, `secret_name`, sealed value, `set_at`, `set_by`).
    - **Key per purpose.** The HKDF info names the owner type, following `TOTPPurpose = "ledger totp secret v1"`: `ledger integration secret v1 setting_group`, `... v1 decision_provider`, `... v1 bank_application`. A key derived for one purpose never opens another purpose's values.
    - **Bound to its row.** The AAD is `owner_type|owner_key|secret_name`, for example `setting_group|oidc|client_secret` or `bank_application|<application id>|private_key`. The owner key is the stable key (the bank application's ULID, never its name, which can change). A sealed value copied to another row or another owner, or restored into the wrong row, does not open. TOTP keeps its AAD (the user id).
    - **Unreadable.** A value that does not open (`Open` returns `ErrUnsealable`: a GCM authentication failure, a wrong prefix or bad base64) is reported, never skipped: the owning resource shows `<name>_set: true` with `<name>_state: unreadable`. An operation that needs it fails with 409 `secret_unreadable`, and the component reports `apply_state: failed` (point 17). Nothing falls back to another source silently. Startup is not refused for an unreadable integration secret, so the person can still replace it through the API.
    - **KEK changes.** Ledger has no KEK rotation (ADR-0030), and the `v1.` format carries no key id. S2 adds a host command, `ledger settings reseal --old-kek-file <path>`. It runs with the server stopped (instance lock, ADR-0019), opens every integration secret with the old KEK, seals it again with the configured one in one transaction, and audits `integration_secret.resealed` (count only). It is safe to run again: a value that already opens with the configured KEK is skipped, and if any value opens with neither the old nor the new KEK, the whole run is refused with nothing changed, listing the owners and secret names (never values). A reseal does not bump the owner's `version`, because the secret's value did not change; the audit entry is the record (point 23's version bump applies to writes through the API). Without it, every integration secret must be written again after a KEK change. The command covers integration secrets only. TOTP secrets keep the ADR-0030 behaviour: recovery codes or `ledger auth reset-2fa`.
    - Loaded secrets are registered with the log redactor.
13. A secret given in the configuration pins that secret: **pinned means the secret's environment variable or its `*_file` key is set.** The API shows the source (`environment`, `dotenv` or `file`) and refuses to write it (409 `setting_pinned`).
    - Today the merchant-enrichment key and the Pulse credentials exist only as file paths (`merchants.enrichment.remote.api_key_file`, `events.pulse.creds_file`, `events.pulse.ca_file`; `.env.example` has only their `*_FILE` variables). The API needs a value to hold, so the tasks add new `config.Config` fields: `merchants.enrichment.remote.api_key` (secret, environment only, like the decision provider keys; S4), `events.pulse.creds` (secret, environment only; S6) and `events.pulse.ca_pem` (not secret; S6). Each new secret field and its `*_file` key are mutually exclusive, as for the existing pairs (`resolveSecretFiles`, `internal/config/validate.go`). The Pulse client then takes the credentials and CA from memory instead of reading the files itself.
14. Banking credentials are never collected: the only bank-related secret is the provider **application's** private key, which belongs to the operator's Enable Banking application, never a bank login.

### 7. Live apply

15. A settings service owns an immutable snapshot of the effective configuration (an atomic pointer). After a write **commits**, it builds and publishes the next snapshot and notifies the components that subscribed to the groups that changed. Requests in flight finish with the snapshot they started with.
16. Every runtime setting applies without a restart. Each component task implements its own reconfiguration: the refresh scheduler and rate service take new intervals at their next tick; sign-in limits, session timeouts and `require_2fa` apply from the next request (a shorter timeout ends sessions that are already older; a longer one never extends a session past what it was issued with); the OIDC verifier, the Enable Banking adapter registry, the Pulse publisher (reconnect), the decision providers and the remote merchant source are rebuilt from the new snapshot.
17. A rebuild that fails after the commit (for example OIDC discovery unreachable) does not roll the setting back: the group reports it in its read-only `apply_state` (`applied`, `failed` or `restart_required`, with an error code and time, never a value), where a component already has a status (rates status, bank connection state) it shows there too, the previous working instance is not kept, and the UI shows the component as failed. Readiness still gates only on the database (D17); Ledger has no general integration status endpoint today, and this ADR does not add one. `restart_required` (added in S1a) means the value is stored and valid but its group has no live consumer yet, so it takes effect at the next start. It lasts only until that start: the next `Open` reports `applied` again. S1 and each group task remove the state for a group once the group has a live consumer. Validation (point 10) refuses everything it can check offline beforehand.

### 8. Grants, recent authentication and the root token

18. Three new resources in the vocabulary (ADR-0021), all administrator-only, each with `read` and `write`: `settings` (application, planning, authentication and operational groups), `integrations` (everything that sends data out or holds an integration secret: bank applications, decision providers, tasks and consents, merchant enrichment, Pulse), and `rules`. Read-only users see none of them; the effects they need (a converted total, a freshness badge) keep coming through the feature that shows them. The existing `rates` resource (FX2c, ADR-0048) is unchanged: it reads the cached rates and asks the provider for fresh ones. Configuring the rate provider (the `rates` group) is `settings`. Existing routes keep their grants, for example `connections:read` on the bank-application reads (point 8).
19. **Sensitive writes** (the "Sensitive" column of point 8, every write-only secret, every egress URL, every consent, and the confirming-rule writes of point 8) need, from a session, a recent sign-in (the existing re-authentication window, `auth.session.reauth_window`), and from a token, **the root token of the root account** (the D25/D32 rule; others get 403 `root_token_required`). Reason: these writes can weaken sign-in, redirect bank or identity traffic to another server, or widen what leaves the process; a leaked ordinary administrator token must not be enough. Control accepted this rule.
    - **Mechanism (S2).** `Access` gains a declarative root-token mode next to `WithRecentAuth`, checked before the handler runs, with the same test as `refuseUnlessRootToken` (a token principal without `CanCreateTokens`). Routes whose every write is sensitive declare it, and their OpenAPI operation carries `x-ledger-root-token: true`. Routes where only some members are sensitive (`banking`, `rates`, rules) declare `x-ledger-root-token: members` with `x-ledger-sensitive-members` listing them, and the handler applies the same check when a patch names one. The same member rule applies to a `DELETE` of such a group: a `DELETE` that resets a stored sensitive member (for example a stored `redirect_url` or `base_url`) is a sensitive write, needs the root token or recent sign-in like any other, and is not available through MCP (point 25); a `DELETE` that resets only non-sensitive members is an ordinary write. Recent authentication follows the same member rule as the root token on these routes. Because the requirement depends on the request, `x-ledger-recent-auth` is false on mixed routes, and `x-ledger-sensitive-members` covers both checks (root token and recent authentication). The OpenAPI parity test in `internal/httpapi/openapi.go` gains both extensions and compares them with the route's declared access and the settings registry. The existing conditional call sites (`users.go`, `sessions.go`) stay as they are.
    - **Sequencing.** Until S2 lands, the generic PATCH and DELETE of S1 refuse every sensitive member as not writable (400 `validation_failed`, "not writable through the API yet"), with a test. So no sensitive group becomes writable without its gate.

19a. **No lock-out.** `internal/config/validate_oidc.go` only checks that `auth.password.enabled=false` comes with `auth.oidc.enabled=true`, and that is configuration alone: with provisioning off and nobody linked, nobody can sign in. An API write that leaves password sign-in disabled (S5) is accepted only when OIDC is **usable**:
    - the effective `oidc` group is enabled and passes validation;
    - the acting person has an OIDC identity linked for the effective issuer, or `auth.oidc.provisioning.enabled` is true (a token acts as its owning user);
    - discovery against the effective issuer succeeds, inside the request, before the commit;
    - and from a session, the recent authentication behind the write is an OIDC sign-in, not a password check. The password that is about to be disabled cannot authorise its own removal when nothing else would be left. Today `sessions.method` records only how a session started. Two routes re-authenticate: `POST /auth/reauthenticate` (a password check) and `POST /auth/oidc/reauthenticate` (ADR-0033; `Service.ReauthenticateOIDC` calls `store.MarkAuthenticated`, which records the method only in the audit detail, not on the session). S5 stores the method in `MarkAuthenticated` for sign-in, password re-authentication and OIDC re-authentication, so the lock-out check accepts a recent `oidc` sign-in or an OIDC re-authentication, and nothing else.
    - A write that fails any of these is 400 `validation_failed` naming the fields involved. The environment break-glass (point 7) and `ledger auth recovery-sign-in` stay the way back.
20. **Audit** (ADR-0025, same transaction as the change): `settings.updated` and `settings.reset` (group, field names), `integration_secret.set`, `integration_secret.cleared` (owner, secret name) and `integration_secret.resealed` (count), `bank_application.created`, `.updated`, `.deleted` (name, mode, field names), `decision_provider.updated`, `decision_task.updated` (field names), the existing `decision_consent.granted`/`revoked`, `rule.created`, `.updated`, `.archived`, `.deleted`. Details carry names, never values (a value may be a URL with a token in it, or a secret). The existing `settings.reporting_timezone_changed` keeps its from/to, is still raised with actor `system` when configuration changes the zone at startup, and is now also raised with the person's or token's identity for an API reclassification (point 6a). Token writes are also covered by `token.write_used`.
21. There is no separate revision table: the audit log keeps who changed which fields when. Control accepted this. A value history would be a later addition (it needs a rule for which values may be kept).

### 9. Storage and migrations

22. One forward-only migration in S1a adds `setting_groups` (ULID `id`, unique `name` checked by pattern (`reporting`, `decision_tasks.categorisation`, ...), `stored` JSON with `json_valid` and only the members set through the API, `version`, `created_at`, `updated_at`). There is one row per singleton group and keyed object, created by Go on its first write (point 9). Migrations are SQL only (`internal/store/migrate.go` runs `m.SQL`, with no Go step per migration), so the migration creates the table and no rows. It follows the versioned convention, so `TestMutableTablesAreVersioned` covers it. The captured reporting zone **does not move**: it stays in the `settings` row that `reporting.Resolve` writes in its own transaction (point 6a), and the `settings` entry in `unversionedTables` stays true. In S3, `Resolve` reads the API `timezone` member from `setting_groups` in the same transaction.
23. S2 adds `integration_secrets` (listed in `unversionedTables`: its owner carries the version, and every secret change bumps it). S7 adds `bank_applications` (versioned). S9 adds a migration for consent attestations: `decision_consents` (migration `0031_decision_providers`) has no attestation column, and its trigger `decision_consents_only_revoked` allows only revocation. The migration adds `attestations` (a JSON array, default `[]`, `json_valid`), and drops and recreates the trigger so attestations are frozen like the other granted members. Rules are X2b's migration.

### 10. Client, CLI, MCP and Terraform parity

24. **Client and CLI** (ADR-0032): every new operation gets a `ledgerclient` method in the task that adds the route (the client's contract test already fails otherwise), and a CLI command: `ledger settings list`, `get`, `set` and `reset <group>` (`set key=value ...`, secrets from `--<name>-file` read on the client machine or from standard input, never a flag value), `ledger bank-applications ...`, `ledger decision-providers ...`, `ledger decision-tasks ...`, `ledger decision-consents ...`, and `ledger rules ...` (X2b).
25. **MCP** (ADR-0038): read tools for every group and object (secrets appear only as set/unset); write tools for `reporting` (a reclassification still needs `reclassify: true`, point 6a), `banking` (without `redirect_url` and `base_url`), `rates` (without `base_url`), `logging`, and rules **without their sensitive writes**: MCP can create and edit non-confirming rules and turn `confirming` off, but cannot create a confirming rule, turn `confirming` on, or change a confirming rule (point 8). **No MCP write tools for the sensitive writes** of point 19 (authentication, OIDC, integrations, secrets, consents, egress URLs, confirming rules): the requirement asks for the *applicable* MCP operations, and a model-driven client is exactly where a prompt-injected change to sign-in, data egress or automatic payment confirmation must not be one call away. A destructive hint is only advice to the client, so the server refuses these writes from MCP whatever the client does. Control accepted this, with the confirming-rule extension.
26. **Terraform** (in terraform-provider-ledger, after the go-ledger pin moves; ADR-0005 B1): one resource per singleton group (`ledger_settings_reporting`, `ledger_settings_auth`, ...; destroy resets), `ledger_decision_provider`, `ledger_decision_task` (destroy resets), `ledger_decision_consent` (replace on change, destroy revokes), `ledger_bank_application`, `ledger_rule`, and a `ledger_deployment_settings` data source. Secrets use `*_wo` with `*_wo_version`; a pinned member is reported as a plan-time error, not as drift.

## Why

- **Configuration pins** rather than the database winning: existing deployments, container setups and the generated examples keep their meaning; the operator always has a path back that needs no working sign-in; and a conflict is explicit (409 with the source) instead of a value silently ignored. Rejected: the database wins (an environment variable would silently stop working); one home per key with keys removed from YAML (breaks every existing deployment and the "YAML, environment and .env configuration" requirement for those keys).
- **`config.Config` as the effective model**: one set of types, defaults, descriptions and validators, so the API cannot accept what startup would refuse and the example file remains the single reference. Rejected: a parallel settings schema (two validations drift).
- **A JSON document per group** rather than typed columns: settings are not financial facts; their rules already live in the configuration validators and are needed there anyway; a key added to `config.Config` needs no migration. The JSON holds only API-set members, so defaults can change between versions.
- **Sealed secrets in the database** next to environment and file secrets: D18 requires secrets to be write-only through the provider, which needs somewhere to write them; the TOTP sealing already exists and is tested.
- **No host paths through the API** and the network-bound keys staying in configuration: these are the exceptions where the API itself would become the attack surface.
- **Root token for sensitive writes**: consistent with D25/D32/D34; Terraform runs with the root token anyway (ADR-0005 point 4).

## Consequences

- Terraform B1 is unblocked group by group; every new route also lands in the client, the CLI and the OpenAPI document, and the coverage table in the provider's ADR-0005 must be re-derived when the pin moves.
- Startup reads the database before the configuration is final; tools that only parse configuration (`config env`, example generation) do not.
- Every component that consumes a runtime setting must handle live change. That is the main cost and the main source of review findings; each task owns its component's test of a change applied without a restart.
- A KEK change now affects integration secrets as well as TOTP. S2 updates the `kek.value` description (today it mentions only TOTP secrets) and adds **new** text to `docs/backup-restore.md`, which has no KEK text today: a backup carries sealed TOTP and integration secrets but not the KEK; restoring it on a host with a different KEK leaves them unreadable; keep the KEK stored safely and apart from the backups; after a KEK change, run `ledger settings reseal` with the old KEK or write the integration secrets again (TOTP: recovery codes or `ledger auth reset-2fa`).
- The reporting zone keeps today's startup behaviour (point 6a). The new behaviour is that an API change of the zone needs an explicit `reclassify`.
- Live apply of the reporting zone is a redesign of `reporting.Service` and its consumers, not wiring. S3 is sized for it.
- Not decided here: nothing. L7 keeps the review UI and the decision settings screens; X3 keeps the TypeSafe consent texts; X2b keeps the rule language and engine.
