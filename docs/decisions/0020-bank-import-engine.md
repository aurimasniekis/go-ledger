# ADR-0020: Bank import engine

Status: Proposed (2026-11-20)

## Context

Task B2 turns the bank-fact store of [ADR-0013](0013-banking-provider-boundary-and-bank-facts.md) into a refresh: repeated and overlapping imports must be safe, every page of a listing must be fetched, an interrupted refresh must resume without duplicates, pending items must become booked where the provider allows it, last-success and attempt times must be recorded, a failed refresh must keep the last good data and show it as stale, an unknown balance must never become zero, and user corrections must survive a refresh.

Inputs: ADR-0013 (keys, immutable source amounts, "B2 and the outlook must exclude pending, superseded and no-longer-reported rows"), decision D8 (pending only suggests; never hard-delete, mark "no longer reported"; explicit purge), D17 (bank data stale after 24 h; retries only for idempotent reads, at most 3, exponential backoff with jitter, honour Retry-After; background logs carry job and job_id), research R1 (continuation keys are bound to session and query; entry references may be missing, repeated or appear only once booked; banks allow about four background fetches a day).

## Decision

1. **Package.** `internal/domain/bankimport` holds the engine. It uses only the `banking.Provider` and `banking.FactStore` ports, so it imports no store or adapter (depguard and the transitive boundary test). Its integration tests live in `internal/store/bankfacts` because domain packages may not import the store, even in tests.
2. **One refresh** (`Engine.Refresh(ctx, connection, provider)`): the provider must be the connection's application and the connection active. It lists accounts, upserts them, marks the connection's unreported accounts *no longer reported*, then per account fetches balances and transaction windows. Provider calls never run inside a write transaction. One engine refreshes a connection at most once at a time (`ErrRefreshInProgress`); across engines the database allows one running run per connection: `StartRefresh` refuses with `ErrRefreshInProgress` while a running run is younger than a lease (`Options.RunLease`, default 30 min, to be set above the longest refresh); only an older one is taken as left by a stopped process and marked `interrupted`. `ErrRefreshInProgress` means "retry later": callers (the scheduler, B4/B6) should show it and try again, not treat it as a failure. After a crash, a restart within the lease cannot refresh that connection until the lease has passed; there is no heartbeat, so a refresh running longer than the lease can be taken over by another engine.
3. **Windows.** Whole days, at most `ChunkDays` (31) long, oldest first. The first refresh reaches back `InitialHistoryDays` (90); later ones resume `OverlapDays` (7) before the account's `transactions_through` cursor, and reach back to the oldest open pending item (not beyond the initial history) so it gets resolved. Nothing reaches beyond the provider's `MaxHistoryDays`. Windows end on today's UTC date. Defaults are options; they are not operator decisions yet.
4. **A window is atomic.** All pages are fetched first (bounded by `MaxPages`, a repeated continuation key is an error), a row that fails `Transaction.Validate` is dropped and counted (`transactions_rejected`; the account shows the notice code `transactions_rejected` until a refresh without one), never failing the window, so the cursor can pass it; such a window marks nothing no longer reported, since a dropped row's stored version must not be taken as gone. The rest is keyed together with `banking.KeyTransactions`, then stored by `FactStore.ImportTransactionWindow` in one write transaction: upsert, mark unreported, link superseded, advance the cursor. An interruption anywhere loses at most the window in flight; nothing partial is written, and the next refresh fetches it again. Idempotent keys make the re-fetch harmless.
5. **No longer reported.** Inside a stored window, every transaction of the account dated in the window (by booking, else value, else transaction date) that the window did not contain is marked `no_longer_reported_at`, never deleted. A row reported again loses the mark (and any superseded link).
6. **Pending to booked.** Same key (entry reference and amount unchanged): booked in place by the B1 upsert; a later pending report cannot undo a booking. New key with the same entry reference (an amount that changed on booking): the pending row is marked no longer reported and `superseded_by` points at the booked row, but only when exactly one booked row of the window has that reference. The link is also made when the pending row was marked earlier (a hold that vanished before its booking appeared, or one dated in another chunk): a booked row upserted with reference R links an unreported, unlinked pending row of the account with reference R under the same exactly-one rule. Amendment: the booked row must be dated on or after the pending row's date and at most 38 days later (`bankfacts.MaxSupersedeGapDays`: the default chunk plus the default overlap), so a reused reference cannot link an unrelated payment; and the late link also requires exactly one such unreported pending row for the reference (with several, none is linked). Without an entry reference the pending row is only marked: linking by amount, date or text would be a guess, and matching safeguards belong to D9.
7. **Counting.** `StoredTransaction.Countable()` is the single rule for anything that counts money: booked, still reported, not superseded. Pending, cancelled, superseded and no-longer-reported rows stay as facts.
8. **Refresh bookkeeping** (migration `0005_bank_refresh`, both tables Ledger-managed, unversioned, RESTRICT to bank facts, deleted only by the connection purge):
   - `bank_refresh_runs`: start, finish, outcome (`running`, `succeeded`, `partial`, `failed`, `interrupted`), error kind and provider code, counts. A run left running by a stopped process becomes `interrupted` when a later run starts after the lease; a finished run is immutable (trigger).
   - `bank_account_sync`: per account `last_attempt_at`, `last_success_at`, last error kind and code, `last_notice_code`, `transactions_through`. A success needs the balances and every window of the account.
9. **Failures.** A failed call writes nothing, so balance snapshots and transactions stay as they were. The account records the error; a connection-level failure (account list, expired consent) records it on every reported account. `reconnect_required` sets the connection status (ADR-0013 `StatusAfter`) and, like a rate limit or cancellation, stops the run; the remaining accounts record the same failure. Other failures fail only their account (balances failing does not skip transactions). A consent known to be expired is not fetched at all, which saves one of the bank's few daily fetches. Bookkeeping uses `context.WithoutCancel`, so a cancelled run is still recorded as interrupted.
10. **Retries (D17).** Only these idempotent reads: a retryable failure, or a rate limit that names a Retry-After, is retried at most three times, with backoff 1 s doubling and jitter in [d/2, d], never sooner than Retry-After. A delay over `MaxRetryWait` (1 min) is not waited for in the run; the error is returned for the scheduler (B6). A rate limit without Retry-After is not retried.
11. **Unknown balances.** A balance without a usable amount and currency is dropped and counted (`balances_rejected`); an account reporting none gets no snapshot. A zero is stored only when the bank reported zero.
12. **Freshness.** `banking.AccountFreshness(connection status, sync, now, staleAfter)` derives `fresh`, `stale` (last success older than 24 h), `failed` (latest attempt failed), `reconnect_required`, `disconnected` or `never_refreshed`, with `Stale` true for all but `fresh`. It is computed, not stored, so it cannot drift from the timestamps.
13. **Corrections.** The engine writes bank facts and its own bookkeeping only. User data lives in its own tables referring to bank facts with `ON DELETE RESTRICT` (ADR-0013 schema test); transaction ids are stable across re-imports and rows are never deleted by a refresh, so a correction keeps its target. A test with a stand-in correction table checks this through booking in place, a rewritten description and a transaction the bank stops reporting.
14. **Observability.** Each run logs with `job=bank_refresh` and `job_id` = the run id, plus Ledger ids, counts and the classified error; never account identifiers, handles, descriptions or payloads. `Options.Meter` takes `internal/metrics`' `JobDone`.

## Why

- Committing per window, not per page, keeps the `#n` ordinals of ADR-0013 stable (identical items are counted over whole days) and makes "interrupted" equal "that window never happened".
- A per-account date cursor is simpler and safer than persisting continuation keys, which R1 binds to the session and query.
- Linking supersession only on a shared entry reference keeps fact-level links free of guesses; D8 keeps pending items out of confirmation anyway.
- Retries stay inside the run but bounded, because banks allow few background fetches; longer waits belong to the scheduler.

Rejected: deleting unreported rows (D8); storing a "stale" flag (it would drift); writing pages as they arrive (ordinals would depend on page boundaries, and an interruption would leave half a window); retrying rate limits without Retry-After (spends the daily budget).

## Consequences

- **Not built here, tracked:** HTTP endpoints to trigger a refresh and to read runs and freshness (with OpenAPI, grants and audit) arrive with the connection API (B4 and the auth tasks); the periodic scheduler and its backoff (B6); `ledger serve` wiring needs a real adapter (B3). No event is published for a refresh: the event catalog's payload allow-list is still open.
- **D8 follow-ups for X1/X2/FX3:** reversals are separate booked bank transactions here; linking them to what they reverse, split and partial allocations, and following `superseded_by` from a match on a pending row to its booked successor belong to X1. A pending row that changed without an entry reference is only marked no longer reported: X1/X2 must treat a match or suggestion on such a row as needing review.
- **Limitations.** The ADR-0013 limitations remain (ordinal shift when a provider drops one of two identical items; repeated references with equal amounts merge). A repeated entry reference with the same amount on different days can get a different ordinal depending on where a window starts. A bank that serves less history than a window asks for would make older rows in that window look unreported; windows only reach back past the cursor for open pending items and never past the provider's known limit, and a later report clears the mark. A transaction dated after today's UTC date (a bank ahead of UTC) arrives with the next refresh. Refresh runs are kept until the connection is purged; their retention is not decided (D17 covers outbox and bank-data staleness only).
- The window, chunk, overlap, history and retry-wait defaults are engine options; exposing them in configuration is left to B6.
